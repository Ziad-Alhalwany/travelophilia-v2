## 3) Risks & Observations
1.  **Constraint Logic in Code vs DB**:
    - Logic for `internal_seq` and `public_code` generation exists heavily in `save()` methods. While `select_for_update` is used in `TripRequest`, complex logic in `save()` can be bypassed by `bulk_create` or `update()`.
2.  **Destructive Migrations**:
    - Migration `trip_requests/0008` removed `lead_seq` and `updated_at` from `reservationsequence`. This is a destructive action (data loss) without a visible data backup step in the migration file. Rollback would restore the column but not the old data.
3.  **Hardcoded Defaults in Models**:
    - Many CharFields have `default=""`. While safe, strictly enforcing `NOT NULL` at DB level is good, but business logic should ensure valid data isn't just empty strings where actual data is expected (e.g. `leader_phone`).

## 4) Actionable Suggestions (Small & Practical)
1.  **Add Database Constraints**: Add `CheckConstraint` in `Meta` for fields that logically shouldn't be empty strings even if valid in Django (e.g. `priceFrom < priceTo`).
2.  **Refactor Code Generation**: Move complex sequence generation from `save()` to a dedicated Service method or Manager method to ensure it's testable and reusable, and less prone to being skipped.
3.  **Migration Safety CI**: Implement a check that warns if a migration file contains `RemoveField` without a corresponding `RunPython` data backup operation.
4.  **Index Optimization**: Review usage of `db_index=True` on `CharterFields` like `leader_phone` or `leader_email` if search performance is critical for CRM lookups (currently only some codes are indexed).
5.  **Soft Delete**: Consider implementing Soft Delete (is_active=False instead of database delete) for `TripRequest` to prevent accidental loss of CRM history.
